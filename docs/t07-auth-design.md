# T07 인증 설계

## 1. 문서 목적

이 문서는 T07 개발의 시작점에서 인증 방식과 사용자 데이터 소유권 구조를 확정하고, 이후 구현에서 따라야 할 기준을 기록한다.

T07은 T06에서 구현한 Plan → Do → See 다이어리에 인증을 추가하는 단계이다.

주요 목표는 다음과 같다.

* 회원가입 / 로그인 / 로그아웃 구현
* 로그인한 사용자의 데이터만 조회 및 변경 가능하도록 제한
* 로그아웃 이후 기존 세션으로 보호된 요청을 수행할 수 없도록 처리
* 기존 T06 데이터를 T07 사용자의 계정에 귀속
* 인증 구현 방식과 접근 제어 근거를 설명할 수 있도록 구조를 명확하게 유지

---

## 2. T07 시작 기준점

T07은 T06의 최종 상태에서 시작한다.

### T06 최종 커밋

```text
d7c571728e20d7e2f7c9a2fcb383c84023b0b67d
```

현재 `main`의 HEAD가 위 커밋과 동일하며, T07 시작 시 working tree는 clean 상태이다.

따라서 T07에서 기존 T06 기능을 다시 구현하지 않고 해당 커밋을 T07의 기준점으로 사용한다.

### 현재 주요 기술 스택

| 항목             | 버전                  |
| -------------- | ------------------- |
| Next.js        | 16.3.4              |
| React          | 19.2.8              |
| Prisma         | 6.19.3              |
| @prisma/client | 6.19.3              |
| TypeScript     | ^5                  |
| PostgreSQL     | Supabase PostgreSQL |

현재 프로젝트에는 다음 Supabase 패키지도 이미 존재한다.

* `@supabase/ssr`
* `@supabase/supabase-js`

그러나 이 패키지가 이미 설치되어 있다는 이유만으로 T07 인증 방식으로 Supabase Auth를 선택하지 않는다. T07의 Database Session 요구사항과 데이터 소유권 구조를 기준으로 인증 방식을 결정한다.

---

## 3. T06의 현재 데이터 구조

T06에는 별도의 User 모델이 없다.

현재 데이터 구조는 다음과 같다.

```text
Plan
├── PlanVersion[]
├── Todo[]
│   └── ExecutionLog[]
└── Review[]
```

Prisma 모델은 다음과 같다.

* `Plan`
* `PlanVersion`
* `Todo`
* `ExecutionLog`
* `Review`

따라서 T07에서는 기존 관계를 최대한 유지하면서 `User`를 소유권의 상위 개념으로 추가한다.

---

## 4. 인증 방식 결정

### 선택한 방식

**Better Auth 1.7.5 + Prisma + Database Session**

T07의 기본 인증 흐름은 이메일/비밀번호 인증으로 구성한다.

인증 관련 데이터는 애플리케이션의 PostgreSQL 데이터베이스에 저장하고, 로그인한 사용자의 세션을 서버에서 검증하는 Database Session 방식을 사용한다.

### 선택한 라이브러리

```text
better-auth 1.7.5
```

Better Auth의 현재 peer dependency 범위는 프로젝트의 주요 버전과 호환된다.

* Next.js 16.x 지원
* React 19.x 지원
* Prisma 6.x 지원
* PostgreSQL 환경 사용 가능

---

## 5. Better Auth를 선택한 이유

### 5.1 Database Session 요구사항과 구조가 일치

T07에서는 단순한 로그인 상태뿐 아니라 다음 동작을 검증해야 한다.

```text
로그인
 ↓
세션 생성
 ↓
보호된 요청 성공
 ↓
로그아웃
 ↓
기존 세션으로 동일 요청
 ↓
요청 거부
```

Better Auth는 데이터베이스 기반 Session 모델을 사용하여 이 흐름을 애플리케이션 데이터베이스와 연결할 수 있다.

따라서 T07에서 요구하는 세션 생성, 검증, 만료, 로그아웃에 따른 세션 무효화를 명확하게 구현하고 검증할 수 있다.

### 5.2 현재 기술 스택과 통합

현재 프로젝트는 이미 Next.js + Prisma + PostgreSQL 구조로 되어 있다.

Better Auth는 Prisma를 인증 데이터 저장소와 연결할 수 있으므로 별도의 인증 서버를 추가하지 않고 현재 애플리케이션 구조 안에서 인증을 구성할 수 있다.

### 5.3 필요한 인증 범위에 적합

T07에서 필요한 기능은 주로 다음과 같다.

* 회원가입
* 로그인
* 로그아웃
* 세션 확인
* 보호된 요청
* 사용자별 데이터 접근 제한

OAuth, 이메일 인증, 비밀번호 재설정 등의 기능은 T07의 핵심 범위가 아니다.

따라서 필요한 인증 기능을 현재 애플리케이션 구조 안에서 구현하는 것을 우선한다.

---

## 6. 검토했지만 선택하지 않은 대안

### 6.1 Supabase Auth

현재 프로젝트에는 이미 다음 패키지가 설치되어 있다.

```text
@supabase/ssr
@supabase/supabase-js
```

Supabase Auth를 사용할 경우 기존 Supabase 인프라와 통합하기 쉽다는 장점이 있다.

그러나 T07에서는 애플리케이션의 PostgreSQL 데이터와 직접 연결된 Database Session 구조와 로그아웃 이후 기존 세션의 무효화를 명확하게 설명하고 검증해야 한다.

따라서 기존에 Supabase 패키지가 설치되어 있다는 이유보다 T07의 인증 및 검증 요구사항을 우선하여 Better Auth를 선택한다.

### 6.2 Auth.js

Auth.js 역시 Prisma를 이용한 데이터베이스 세션 구성이 가능하다.

그러나 이번 T07에서는 OAuth나 다양한 인증 제공자보다 이메일/비밀번호와 Database Session을 중심으로 필요한 기능을 구성하는 것이 목적이다.

따라서 인증 범위를 단순하게 유지하기 위해 Better Auth를 선택한다.

### 6.3 직접 인증 구현

User, password hashing, session token, cookie, expiration, logout invalidation 등의 인증 로직을 직접 구현하는 방법도 검토할 수 있다.

하지만 직접 구현할 경우 인증과 세션 관리에 필요한 보안 로직을 애플리케이션에서 직접 관리해야 한다.

T07의 목표는 인증 시스템을 처음부터 구현하는 것보다 인증을 적용하고 그 동작과 접근 차단을 검증하고 설명하는 것이므로 인증 라이브러리를 사용한다.

---

## 7. 비밀번호 저장 방식

Better Auth의 기본 이메일/비밀번호 인증은 비밀번호를 원문으로 저장하지 않고 `scrypt` 기반으로 해시한다.

T07에서는 비밀번호를 평문으로 데이터베이스에 저장하지 않는다.

기본 원칙은 다음과 같다.

```text
회원가입
 ↓
사용자가 입력한 비밀번호
 ↓
scrypt 기반 해시
 ↓
Database
```

로그인 시에는 저장된 해시와 사용자가 입력한 비밀번호를 검증한다.

또한 T07 검증 과정에서 다음 항목을 확인한다.

* 데이터베이스에 입력한 원문 비밀번호가 저장되지 않는지
* 동일한 비밀번호를 사용하는 서로 다른 계정의 저장값이 동일하지 않은지
* API 응답에 비밀번호가 포함되지 않는지
* 서버 로그에 비밀번호가 출력되지 않는지
* 제출 자료에 실제 비밀번호가 포함되지 않는지

---

## 8. 사용자 데이터 소유권 구조

T07에서는 `Plan`을 기존 T06 데이터의 소유권 루트로 사용한다.

목표 구조는 다음과 같다.

```text
User
└── Plan
    ├── PlanVersion
    ├── Todo
    │   └── ExecutionLog
    └── Review
```

### 소유권 판단

각 데이터의 소유자는 기존 관계를 따라 `Plan`에서 확인한다.

```text
Plan
 ↓
User

Todo
 ↓
Plan
 ↓
User

ExecutionLog
 ↓
Todo
 ↓
Plan
 ↓
User

PlanVersion
 ↓
Plan
 ↓
User

Review
 ↓
Plan
 ↓
User
```

따라서 모든 하위 모델에 `userId`를 중복해서 추가하지 않고 기존 관계를 이용해 소유권을 확인한다.

---

## 9. 사용자 식별 원칙

사용자 소유권은 클라이언트가 전달한 `userId`를 신뢰하여 결정하지 않는다.

보호된 요청에서는 서버가 현재 세션을 검증하고 세션에 연결된 사용자의 ID를 가져온다.

```text
Request
 ↓
Session 검증
 ↓
session.user.id
 ↓
Plan.userId 조건으로 데이터 조회
 ↓
현재 사용자의 데이터만 반환
```

예를 들어 클라이언트가 다른 사용자의 ID를 요청에 포함하더라도 해당 값을 소유권 판단의 기준으로 사용하지 않는다.

이 원칙은 T07의 사용자 간 데이터 접근 차단 검증에서도 동일하게 적용한다.

---

## 10. 기존 T06 데이터 마이그레이션

T06에서는 User 모델이 없었기 때문에 기존 데이터에는 사용자 소유권 정보가 없다.

T07에서는 기존 T06 데이터를 보존하면서 특정 T07 사용자 계정에 귀속시킨다.

목표는 다음과 같다.

```text
기존 T06 데이터
       ↓
T07 사용자 계정 생성
       ↓
기존 Plan에 해당 User 연결
       ↓
Plan을 통해 기존 하위 데이터의 소유권 확인
```

기존 Plan, Todo, ExecutionLog, PlanVersion, Review의 실제 데이터는 가능한 한 그대로 보존한다.

---

## 11. 보호 대상

T07에서는 인증이 필요한 데이터 접근 경로를 보호한다.

주요 대상은 다음과 같다.

* Plan 목록
* Plan 상세 조회
* Plan 생성 / 수정 / 삭제 / 복구
* Todo 관련 데이터
* ExecutionLog
* PlanVersion
* Review
* Review 집계 화면
* `/api/export`

인증되지 않은 요청은 보호된 데이터에 접근할 수 없어야 한다.

또한 로그인한 사용자라도 다른 사용자의 데이터를 직접 식별자로 지정하여 접근할 수 없어야 한다.

---

## 12. 세션 검증 원칙

T07에서 세션은 단순히 브라우저에 로그인 여부를 표시하기 위한 값으로 사용하지 않는다.

보호된 요청마다 서버 측에서 현재 세션의 유효성을 확인한다.

검증해야 할 주요 조건은 다음과 같다.

1. 세션이 존재하는가
2. 세션이 만료되지 않았는가
3. 세션에 연결된 User가 존재하는가
4. 요청 대상 데이터가 현재 User의 소유인가

로그아웃 시 현재 세션을 무효화한다.

따라서 로그아웃 전에 확보한 기존 세션 값을 이용해 같은 보호된 요청을 다시 보내더라도 서버에서 요청을 거부할 수 있어야 한다.

---

## 13. T07에서 구현하지 않는 기능

이번 단계에서는 다음 기능을 구현 범위에 포함하지 않는다.

* OAuth 로그인
* 소셜 로그인
* 이메일 인증
* 비밀번호 재설정
* 관리자 계정
* 역할 기반 권한 관리(RBAC)
* 사용자 프로필 기능
* 별도의 관리자 페이지
* T07 요구사항과 직접 관련 없는 인증 기능

새로운 인증 관련 기능이 필요해질 경우 기존 Issue 범위를 임의로 확장하지 않고 별도의 Issue로 관리한다.

## 14. T07 인증 검증 계획

구현 완료 후 다음 시나리오를 검증한다.

### 기본 인증

```text
회원가입
→ 로그인
→ 보호된 데이터 접근 성공
→ 로그아웃
→ 로그아웃 상태에서 보호된 데이터 접근 거부
```

### 세션 무효화

```text
로그인
→ 기존 세션 값 확보
→ 보호된 요청 성공
→ 로그아웃
→ 동일 세션 값으로 동일 요청
→ 요청 거부
```

### 사용자 간 접근 제어

```text
User A
├── A의 Plan
└── A의 Todo

User B
├── B의 Plan
└── B의 Todo
```

다음 접근을 모두 검증한다.

```text
A → A 데이터       허용
B → B 데이터       허용

A → B 데이터       거부
B → A 데이터       거부
```

조회뿐 아니라 수정 및 삭제에서도 동일한 소유권 검사를 적용한다.

---

## 15. 제출 자료에 사용할 핵심 설명

T07 최종 제출에서는 인증 구현을 다음 여섯 항목으로 설명한다.

1. **무엇을 사용했는가**
2. **왜 선택했는가**
3. **어디를 어떻게 변경했는가**
4. **무엇이 차단되는지 어떤 증거로 확인했는가**
5. **AI가 한 것과 직접 판단한 것은 무엇인가**
6. **아직 무엇이 차단되지 않는가**

특히 6번 항목은 빈칸으로 두지 않는다.

실제 구현 및 검증 과정에서 확인된 한계나 T07 범위 밖의 미구현 영역을 구체적으로 기록한다.

## 16. 설계 결정 요약

```text
인증
└── Better Auth 1.7.5

인증 방식
└── Database Session

비밀번호
└── scrypt 기반 해시

DB
└── PostgreSQL + Prisma 6.19.3

사용자 데이터
└── User
    └── Plan
        ├── PlanVersion
        ├── Todo
        │   └── ExecutionLog
        └── Review

소유권 판단
└── 서버에서 검증한 session.user.id
    └── Plan.userId

기존 T06 데이터
└── T07 사용자 계정에 귀속

주요 검증
├── 로그인 전 접근 차단
├── 로그인 후 본인 데이터 접근
├── 로그아웃 후 기존 세션 무효화
├── 사용자 간 조회 차단
├── 사용자 간 수정 차단
└── 사용자 간 삭제 차단
```

이 문서는 T07 #13의 설계 기준이며, 이후 구현 과정에서 실제 동작과 다른 부분이 발견되면 해당 Issue에서 근거를 확인한 후 문서를 갱신한다.
